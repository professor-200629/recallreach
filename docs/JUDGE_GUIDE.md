# Reproducing RecallReach's results (for judges and reviewers)

**Fastest: no install.** Open the public demo at <https://recallreach-demo.balu04t.workers.dev>, choose **Explore a mock recall**, then try **Why this finding?** on the 40 bottles and **Agent → Investigate** (rules mode). It has no live model and no Zetaris connection; each browser gets its own sandbox with fictional data.

Everything below runs locally on fictional data. Steps 1–4 need only Node.js (≥ 22.13) and about 10 minutes; nothing is sent over the network. Steps 5–6 are optional and need a model key or a Zetaris instance.

**Verified from a fresh clone** on 26 Oct 2026 (Windows 11, Node 24.14, commit `fa2b1be`, no `.dev.vars`): `npm ci`, `npm test` (144 of 144 pass), `npm run typecheck`, `npm run lint`, `npm run build`, `npm run db:migrate:local`, then `npm run dev`. In the app, the drill case was created and a rules-mode investigation completed with 6 of 6 typed facts validated (1,000 accepted, 40 available, 60 dispensed); Zetaris showed as not configured, as expected without settings.

```bash
npm ci

npm run typecheck
npm run lint
```

Expected: all tests pass, and typecheck and lint are clean (counts in [EVALUATION.md](EVALUATION.md)).

## 2. Reproduce the reviewer's counterexamples

Each of these was reported against an earlier version and is now a test that must fail safely:

| Counterexample | Test |
| --- | --- |
| "RR-104 has 60 bottles dispensed" accepted because 60 dispensed appears elsewhere | `tests/trust.test.ts` (first test); `tests/facts.test.ts` "wrong shipment" |
| Wrong state, wrong unit, wrong scope (shipment vs case), stale snapshot, evidence never retrieved | `tests/facts.test.ts` |
| Mixed clauses or an unsupported summary reaching the checked summary | `tests/facts.test.ts` "mixed clauses…" |
| A record named by a memory or an issue list used as evidence without retrieving it | `tests/trust.test.ts`, `tests/facts.test.ts` "referenced is not delivered" |
| A memory with no trackable dependency shown as current; connected-source evidence never rechecked | `tests/trust.test.ts` |
| Tool output cut into invalid JSON | `tests/trust.test.ts` (last test) |
| Re-import double counting, same-key corrections, more than 500 rows, a failed page, equal keys from two instances, a disappeared row | `tests/import.test.ts` |
| Case saved without its memory (or the reverse); concurrent runs | `tests/boundaries.test.ts` |
| Forged identity headers; work continuing after the deadline | `tests/boundaries.test.ts` |

Run one file: `node --experimental-transform-types --no-warnings --test tests/facts.test.ts`.

## 3. Reproduce the evaluation

```bash
npm run eval        # writes eval/results.json; no model, no network
```

It compares the spreadsheet-style baseline, the deterministic engine and the agent in rules mode on four fictional cases. Two of them are held out: `eval/heldout/corvel-vials.ts` (key `1313452`) and `eval/heldout/halvex-tablets.ts` (key `9237cc1`, written after the first case's live runs). `eval/results.json` is regenerated by this command; the live results files are never overwritten. Check that each held-out answer key came first and has not changed since:

```bash
git log --format="%h %ad %s" --date=iso -- eval/heldout/corvel-vials.ts
git log --format="%h %ad %s" --date=iso 1313452..HEAD -- eval/results.json "eval/results-live-corvel-vials*.json"
git log --format="%h %ad %s" --date=iso -- eval/heldout/halvex-tablets.ts
git log --format="%h %ad %s" --date=iso 9237cc1..HEAD -- eval/results.json "eval/results-live-halvex-tablets*.json"
git log --oneline 1313452..HEAD -- lib/recall/engine.ts
```

The first and third commands print only `1313452` and `9237cc1` (each fixture and its key, committed alone). The second and fourth list every later commit that added or changed that case's results. The last prints nothing: the engine has not changed since the first key was frozen. Other code did change after results were seen; EVALUATION.md §2 says which and why. The same developer wrote the engine, the fixtures and the keys, so these are not independent accuracy measurements.

Open `http://127.0.0.1:5173/signin-with-chatgpt?return_to=/` (a local test sign-in that only works on your machine; the dev server listens on 127.0.0.1), then **New case → The missing 40 bottles**. ## 5. Optional: a live model

Put your own `GROQ_API_KEY` in `.dev.vars`. Groq's free tier was used: it allows 8,000 tokens per minute and 200,000 per day, so a run spends most of its time waiting and can use up to its 8-minute limit (`AGENT_TIME_LIMIT_S` changes it), each request is kept under 8,000 tokens (`AGENT_MAX_REQUEST_TOKENS`), and a few runs use up a day's allowance. Then choose **Live model** in the app, or:

```bash
node --env-file=.dev.vars --experimental-transform-types --no-warnings scripts/evaluate.ts --live --runs 1 --only corvel-vials --tag my-run
```

`--only halvex-tablets` runs the second held-out case instead. Each live series is written to its own file (`eval/results-live-corvel-vials-my-run.json`); the script refuses to overwrite an existing live results file. Live results vary between runs; EVALUATION.md records every run made for the submission, including failures.

## 6. Optional: Zetaris

The Zetaris integration was verified on a local Zetaris 2.4.3 instance with three fictional PostgreSQL source databases. Reproducing it needs Docker, the hackathon's Zetaris download and about an hour; follow [INTEGRATIONS.md](INTEGRATIONS.md). Without it, the app runs on CSV imports, and a clearly labelled mock (`RECALLREACH_MOCK_SOURCES=1`) exercises the same code path; it is never presented as Zetaris.

## What cannot be reproduced here

- The full app hosted with sign-in, a live model or Zetaris: only the public demo (rules mode) is hosted (see DEPLOYMENT.md).
- Real recall data or real users: none were used.
